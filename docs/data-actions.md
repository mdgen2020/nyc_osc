## Existing action: not reused

`miked_SecurityCodeGenerator` (`753dd321-a959-40c9-92f3-ebe5e65b1f77`) is **not compatible**: `length` and `characters` are caller inputs, the default character set `012345679` omits `8`, and the output is an unconstrained string, so nothing guarantees `^[0-9]{6}$` or preserved leading zeros. It is left unchanged. A new `mikedai_OSC_SecurityCodeGenerator` takes no input, and the Edge Function uses a cryptographically secure RNG with rejection sampling (no modulo bias) and `padStart(6, "0")`. A test samples 20,000 codes and requires at least one leading zero.

## Why eight and not two

An earlier plan used two actions (the generator plus one consolidated `ClaimOperations`). It was dropped because AVA tools take at most about five inputs, there is no constant input source to pin an `operation` field, and a shared mega-schema weakens typing. Deterministic steps are instead consolidated **server-side** (check-plus-send, status-plus-documents-plus-payment), which is what keeps the count at eight.

## Contract guarantees (tested)

- Real backend responses match each declared output schema (`additionalProperties: false`).
- Declared output properties equal the handler's allow-list (`GENESYS_OUTPUT_KEYS`), so no field can leak.
- AVA output types in the design artifact match the contracts (names, primitives, arrays, required flags).
- Inputs are validated against the declared schemas; undeclared fields and malformed codes are rejected.
- The code is never in any response; a forged token yields `VERIFICATION_REQUIRED`.
